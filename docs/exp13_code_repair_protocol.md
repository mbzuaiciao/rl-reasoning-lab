# EXP-013 · Code repair protocol

[Issue #13](https://github.com/mbzuaiciao/rl-reasoning-lab/issues/13) asks whether test feedback gives a useful training-free process signal. EXP-011 found that malformed traces and premature stopping can obscure reward differences; EXP-012 found that reward variation can coexist with an outcome floor. Here we compare candidates for the same task against separately held acceptance cases.

- Freeze the eight task specifications and buggy functions, 24 public cases, 32 hidden cases, and the prompt via the SHA-256 hashes in the runner. The model receives the spec, buggy function, and three public input/output examples only. It never sees the hidden file, reference solutions, earlier candidates, or their scores. Hidden cases are held out from the model, though the published artifact makes them visible to readers.
- Use the cached pretrained Qwen2.5-0.5B-Instruct snapshot and hashes from EXP-012, with its chat template, FP32 on four CPU threads and offline Transformers. Sample three independent candidates per task in fixture order, with seeds 13001–13024, temperature 0.8, top-p 0.95, no top-k cutoff and at most 160 new tokens. Keep duplicates and format failures; no retries or model/prompt selection based on the pilot. Do not begin the pilot without a passing isolation check, reference controls, and an offline model smoke decode on an unrelated input. Cap the pilot at 600 seconds from the end of preflight and retain completed results if stopped.
- A patch replaces one function: accept bare Python or a single Python fence, require a single synchronous function with the original plain positional signature, and reject code that cannot compile. Apply only to a disposable container. No repository or other host mounts, no network, no credentials, no extra Linux capabilities; use a non-root UID, read-only root, default seccomp and no new privileges. Each case runs in a fresh local Docker container with memory, PID, CPU, output and wall bounds. Send only the candidate and one case's inputs. Compare its JSON result to the expected value on the host. A case that errors or exceeds a limit fails; infrastructure failures stop the run. Never fall back to host execution.
- Report applicability over all samples. For applicable candidates record each public and hidden case, public pass fraction, change versus the buggy function, and regressions (previously passing case IDs now failing, by split). Hidden success means all four hidden cases pass. Report separately whether any hidden success still fails a public test. Invalid patches have undefined test measurements and fail final acceptance; omit them from reward rankings and from the mixed-task gate so formatting alone cannot satisfy it.
- Within each task compare the public improvement of every applicable hidden-success/hidden-failure pair; report concordance, ties and inversions. Among applicable hidden failures report the count with positive public improvement, the count that pass all public cases, and regression examples. Read all outputs for exact-input branching, hardcoded returns, grading manipulation, or evidence that hidden data reached generation. Public overfitting is distinct from hidden data leakage.

**Frozen go/no-go gate for a separate RL proposal:** Require a complete pilot, at least four tasks with both an applicable hidden-success and an applicable hidden-failure patch, at least four applicable hidden-failure patches with strictly positive public improvement, and no evidence of test leakage. The last condition requires review of the run; it cannot be inferred from scores. If preflight is blocked or the pilot is incomplete, report no-go with the reason. This is a descriptive gate.
