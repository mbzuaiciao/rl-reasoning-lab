# EXP-015 · Frozen repair feasibility protocol

[Issue #17](https://github.com/mbzuaiciao/rl-reasoning-lab/issues/17) · [EXP-013 protocol](exp13_code_repair_protocol.md) · [EXP-014 report](exp14_model_selection_report.md)

Use eight original Python functions with three public diagnostics and four local acceptance cases apiece. The runner verifies the SHA-256 of both fixture files and the EXP-013 prompt template. Generation receives only the specification, buggy function and three public cases. The acceptance cases and reference functions are published development fixtures. Keep each completion, including duplicates, inapplicable outputs and outputs at the token cap.

Use EXP-014's pinned Qwen3.5-4B GGUF and llama.cpp build, with four CPU threads, a 1,024-token context and direct answers. Use three independent draws in fixture order with seeds 15001–15024, temperature 0.8 followed by top-p 0.95, no top-k cutoff, no prompt cache and a 160-token cap. Run the established Docker isolation and resource probes, all reference and buggy controls, and a separate offline smoke decode before starting the 600-second pilot. Generate the frozen sequence before grading so an interruption in grading can be recovered from the saved completions. Sample only once per slot.

Use the `desktop-linux` context and existing per-user socket as a regular macOS user. Use the pinned EXP-013 evaluator image and its unchanged isolation controls. If the daemon is unavailable, stop and keep the report incomplete. Record infrastructure errors as missing and regrade saved, verified patches only after the isolation and fixture controls pass again. No host execution of model output.

Use the EXP-013 replacement parser and scoring. Applicability means a compilable replacement with the original function name and positional signature. Public feedback is the fraction of three diagnostics passed, with improvement measured against the buggy function. The terminal acceptance outcome requires all four local acceptance cases. Record per-case regressions against the buggy function on both splits. For each task, compare the public score of every applicable accepted/rejected pair and count correct orderings, ties and inversions. Check for public-score saturation, full-public failures, regressions masked by the aggregate, exact-input hardcoding, grader manipulation and leakage.

**Go only if** the pilot is complete, at least four tasks have both an accepted and a rejected applicable patch, at least four applicable rejected patches improve the public score, and review finds no evidence of answer leakage or unsafe evaluation. The counts are descriptive. Candidate rankings assess the diagnostic signal available for selection. The pilot samples independently and never feeds scores back to the model.
